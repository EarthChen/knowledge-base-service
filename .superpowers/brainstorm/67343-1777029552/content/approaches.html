三种实施方案对比

基于已确认的需求：双路代码获取 + 百科模式 + 分层生成

A

渐进增强方案 ⭐ 推荐

分三阶段逐步增强现有 wiki 系统，每阶段独立交付价值

Phase 1 — 代码感知层（~2天）
• SourceCodeReader: 利用图节点 file/line + Chunk.text 读取精准代码
• 修改 WikiDataCollector → PageData 增加 code_snippets
• 增强 _entity_digest → 在 LLM prompt 中嵌入实际代码
• 效果: 立刻从"看元数据"升级到"看真实代码"
Phase 2 — RAG 检索层（~3天）
• 为 67K Chunk 批量生成 embedding（利用已有 embedding pipeline）
• ChunkRetriever: 语义检索相关代码片段
• 两路合并: 精准代码(Phase1) + 语义关联代码(Phase2)
• 效果: 跨文件关联，发现隐式依赖
Phase 3 — 百科分层生成（~3天）
• 多层 Prompt 模板: 基础层 → 业务分析层 → FAQ/示例层
• 异步丰富管道: 先推送基础版，后台逐层补充
• 效果: 快速可见结果 + 最终完整百科内容

优势

  • 每阶段独立交付，风险可控
  • Phase 1 见效最快
  • 复用最多现有基础设施

劣势

  • 总工期最长 ~8天
  • 三次部署发布
B

一步到位方案

一次性实现所有功能，作为完整的 wiki 2.0 发布

整体重构 WikiComposer（~6天）
• 新的 WikiComposer2 替换现有 composer
• 内置 SourceCodeReader + ChunkRetriever + 多层 Prompt
• 统一的 Context Assembly 管道
• 完整的百科模板系统

优势

  • 架构更整洁
  • 一次性完成

劣势

  • 开发周期长，期间无产出
  • 风险集中在一次发布
  • 调试困难
C

最小可行方案

只做代码感知层，RAG 和百科模式暂不实施

仅 Phase 1（~2天）
• 只做运行时源码读取 + Chunk.text 利用
• 增强 prompt 模板
• 不做 RAG，不做多层生成

优势

  • 最快见效
  • 改动最小

劣势

  • 无语义检索能力
  • 内容深度有限
  • 后续仍需额外工作
