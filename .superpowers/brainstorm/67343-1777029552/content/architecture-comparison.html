Wiki 生成增强：当前架构 vs DeepWiki 方式

理解差异，找到最佳增强路径

📦 当前架构（图谱元数据驱动）
① 代码索引
源代码 → AST 解析 → FalkorDB 图节点
存储: name, signature, docstring(截断), start_line/end_line
❌ 不存储完整函数体/类体
② 数据采集
WikiDataCollector.collect() → PageData
包含: 节点属性 + edges + children + methods
❌ 无实际代码内容
③ LLM 生成
_entity_digest() → 纯文本描述
传给 LLM: 属性列表 + 关系摘要
❌ LLM 看不到实际代码逻辑
⚡ 结果
生成内容偏结构化/概述型，缺乏业务深度
🚀 DeepWiki 方式（RAG 代码检索驱动）
① 代码索引
源代码 → 文件切片 → Embedding → 向量库
存储: 代码片段原文 + 向量表示
✅ 保留完整代码内容
② RAG 检索
每页生成前检索相关代码片段
语义搜索 + 路径匹配 → Top-K 代码块
✅ 精准获取相关源码
③ LLM 生成
结构化 Prompt + 实际代码片段
传给 LLM: 代码 + 文件路径列表 + 结构信息
✅ LLM 可理解真实业务逻辑
⚡ 结果
生成内容详细、有代码引用、理解业务流程

🔑 关键差异：LLM 上下文中是否包含实际代码

我们的系统已有 图谱结构（关系、层级、调用链）这是 DeepWiki 不具备的优势。
增强方向是：在保留图谱结构的同时，引入 RAG 代码检索，让 LLM 在理解架构的同时也能看到关键代码。
