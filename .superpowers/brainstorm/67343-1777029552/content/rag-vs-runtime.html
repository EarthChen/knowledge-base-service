方案对比：RAG 向量检索 vs 运行时源码读取

结合你的实际场景做决策

🔍 B) RAG 向量检索层
工作原理
索引时：源文件 → 切片(~200行) → Embedding → 向量库
生成时：用实体名/FQN 检索 → Top-K 代码片段 → 送入 LLM

✅ 优势

  • 语义检索 — 可以找到"相关"而非"精确匹配"的代码
  • 跨文件关联 — 一个实体能检索到多个相关文件片段
  • 不依赖本地文件 — 索引后源码可以不在本地
  • 适合大型项目 — 检索效率不受项目规模影响

❌ 劣势

  • 新增组件 — 需要向量存储(但已有 embedding 能力)
  • 索引耗时 — 全量索引需要计算大量 embedding
  • 可能过时 — 向量索引与源码版本不同步
  • 实现复杂度高 — 切片策略、检索排序需要调优
📂 C) 运行时源码读取
工作原理
图节点已有：file, start_line, end_line
生成时：读取 file[start:end] → 截取代码 → 送入 LLM

✅ 优势

  • 零新增组件 — 直接用现有图谱数据
  • 始终最新 — 读的是当前文件，无同步问题
  • 精准定位 — 图谱关系告诉你"该读哪个函数"
  • 实现简单 — ~100行代码即可完成

❌ 劣势

  • 依赖本地文件 — 源码必须在服务可达路径
  • 无语义检索 — 只能读图谱明确指向的代码
  • 行号可能漂移 — 代码修改后行号可能不准
  • IO 开销 — 大型页面需读多个文件

💡 我的推荐：C 先行，B 后补

阶段 1（本次实施）：运行时源码读取
• 你的服务和代码仓库在同一台机器上（开发机部署）
• 图谱已经有精确的 file/line 信息
• 实现快速（~100行），立刻能看到效果提升
• 图谱的结构关系 + 精准代码读取 = 已经远超 "只看元数据" 的质量

阶段 2（未来可选）：叠加 RAG 检索
• 当需要"跨文件语义关联"时再引入
• 用向量检索补充图谱未覆盖的隐式关系
