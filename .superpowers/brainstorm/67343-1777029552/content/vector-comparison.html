向量存储选型：A vs C 深度对比

两者实际上指向同一个技术底层，区别在于"索引什么"

🔑 关键发现：你的系统已经具备完整的向量能力

FalkorDB 已建立向量索引（FUNCTION, CLASS, MODULE, CHUNK 等 8 种 label），
vector_search() 方法也已实现。
选项 A 和 C 本质上用的是同一套基础设施，区别仅在于索引的内容。

📊 C) 现有 embedding 能力
现状
• 已有向量索引: FUNCTION, CLASS, MODULE, CHUNK 等
• 已有 set_node_embedding() 写入
• 已有 vector_search() 检索
• embedding 存在图节点的 embedding 属性上
当前用于
• WikiPage 相似度搜索
• 代码节点语义搜索（Deep Search）
• 但代码节点的 embedding 是基于名称/签名生成的
• 不是基于完整代码内容
能做什么
直接用 vector_search(NodeLabel.FUNCTION, query_embedding) 找到语义相近的函数节点，但节点上没有代码内容 → 还是需要回读源文件
🚀 A) FalkorDB 向量索引（增强版）
需要做的
• 新增 CHUNK label 的向量索引（已存在！）
• 索引时切片源代码文件 → 创建 CHUNK 节点
• CHUNK 节点存储：原始代码文本 + embedding
• CHUNK 节点通过 CONTAINS 关联到 MODULE/CLASS
优势
• 向量检索 → 直接返回代码文本（不需要读文件）
• 语义搜索 → 找到与主题相关但非直接引用的代码
• 与图谱天然融合 → CHUNK → MODULE → CLASS 关系链
结论
在 C 的基础上做增量：利用 CHUNK label + 存储代码文本到节点属性 + 关联到代码结构图

💡 结论：A = C + 代码内容索引

两者用的是 同一套 FalkorDB 向量基础设施。
选 A 本质就是："在已有向量能力(C)的基础上，把源代码文件切片为 CHUNK 节点存入图谱"。

推荐路径：
① 先用运行时文件读取（已有 file/line 精准定位）— 立刻见效
② 再在索引阶段创建 CHUNK 节点（存代码文本 + embedding）— 实现语义检索
③ wiki 生成时两路合并：精准代码（来自文件读取）+ 相关代码（来自向量检索）
