# Wiki 系统深度审阅报告 — 2026-05-01

> **审阅范围:** 后端 119 个 wiki 模块 + 前端 102 个 wiki 组件/hooks + 1403 个测试  
> **方法:** 3 个并行探索代理 + sequential-thinking 8 轮深度分析  
> **对标项目:** [DeepWiki-Open](https://github.com/AsyncFuncAI/deepwiki-open) (15.3K ⭐)、[CodeWiki](https://github.com/FSoft-AI4Code/CodeWiki) (ACL 2026)  
> **前置工作:** 上轮审计 19/19 项已修复 (2026-04-30)

## 1. Executive Summary

KB Service 在增量更新、多视图、Agent MCP、记忆演化、导出生态方面保持显著领先。上轮审计修复后代码质量良好（1403 测试全通过、0 warnings）。

本轮审阅聚焦 **三个核心改进方向**：
1. **提示词工程升级**：当前所有 LLM 提示词采用 "one-shot direct output" 模式，缺乏思维链引导，导致内容质量上限受限
2. **竞品功能追赶**：与 DeepWiki/CodeWiki 在内容生成智能度、结构规划、代码视图方面仍有差距
3. **架构/前端技术债务**：循环依赖、并行实现、i18n 不一致等问题

## 2. P0 — 提示词工程审阅

### 2.1 当前提示词模式分析

| 节点 | 当前模式 | 问题 |
|------|---------|------|
| `classify_domains_node` | JSON-only direct output | 无中间推理，域分类"凑数" |
| `decompose_hierarchy` | Constraints + JSON output | 无聚合度/耦合度分析 |
| `compose_pages_node` | Flat prompt → Markdown | 内容僵化，缺乏叙事性 |
| `heal_pages_node` | bench hints + full regen | 不是定向修复，而是重写 |
| `synthesize_overviews_node` | 仅用前200字符 | SystemOverviewComposer 未复用 |
| `quality_gate_node` | structural_check (规则) | llm_judge_evaluate 未接入 |

**共性问题：**
- 零 chain-of-thought 引导
- 仅 `semantic_diagram_gen` 有 1 个 few-shot 示例
- `cot_generator.py` 已存在两步 CoT 实现但 `cot_enabled=False` 且未接入 LangGraph 管道
- `prompts.py` 中的 `DOMAIN_CLASSIFY_PROMPT` / `TOPIC_STRUCTURE_PROMPT` 仅测试引用，与生产代码脱节

### 2.2 CoT 引入方案

**推荐策略：混合方案 (显式两步 + LLM 原生 thinking)**

| 节点 | 方案 | 说明 |
|------|------|------|
| 域分类 | 显式两步 | Step1: 分析模块间调用关系和业务边界 (JSON)；Step2: 基于分析进行分类 |
| 层级分解 | 显式两步 | Step1: 评估每个域的内部聚合度和域间耦合度；Step2: 决定是否需要子域拆分 |
| Topic 生成 | LLM 原生 thinking + prompt 增强 | 仅 MEDIUM/HIGH 复杂度域启用；prompt 增加"分析核心职责和协作模式" |
| Heal | 显式两步 | Step1: 诊断当前页面的具体缺陷 (JSON)；Step2: 针对性修改而非重写 |
| System Overview | 复用 SystemOverviewComposer | 替代 thin ad-hoc 实现 |
| Quality Gate | 接入 llm_judge | CORE tier 页面启用 L3 质量评估 |

**实施约束：**
- 分类等轻量任务使用快速模型 (无 CoT)，避免 Qwen3 thinking 延迟
- 通过 `thinking_budget` 参数控制 CoT 深度
- 仅在影响整体架构准确性的决策节点引入显式两步 CoT

### 2.3 提示词集中化管理

- **问题**: `prompts.py` 模板与生产代码使用的内联字符串不一致
- **建议**: 将所有 LLM prompt 迁移到统一的 prompt registry，按 `(node, version)` 索引
- **收益**: 可追踪 prompt 版本变更对生成质量的影响

## 3. P0 — 管道质量保证

### 3.1 质量门分层不足

- **现状**: `quality_gate_node` 仅用 `structural_check` (规则引擎)
- **问题**: 页面可有正确 heading/长度/图表但内容重复或幻觉
- **建议**: 三层质量门

| 层级 | 检查 | 适用 | 成本 |
|------|------|------|------|
| L1 structural | 规则检查 (heading/length/diagrams) | 所有页面 | 0 |
| L2 depth | bench_score (深度+图表多样性+链接) | STANDARD+ | 0 |
| L3 llm_judge | LLM 评分 (完整性/帮助性/真实性) | CORE tier | 1 LLM call |

### 3.2 Heal 策略低效

- **现状**: heal 是完全重写 (regen)，如果 LLM 一致性低，heal 无效
- **建议**: 改为 targeted patch
  - 基于 bench_score issues 生成定向修改指令
  - 例: "在 ## 核心业务流程 中添加 Mermaid sequenceDiagram" 而非重写整页
  - 保留已通过检查的 sections

### 3.3 Mermaid 图表质量

- **现状**: 仅 `sanitize_mermaid_output` 检查格式 (起始关键字 + 行数)
- **问题**: 语法正确但业务语义可能错误
- **建议**: 添加 Mermaid syntax parse 验证 (可用 mermaid-js 的 parse API)

## 4. P1 — 竞品差距分析

### 4.1 对比 DeepWiki

| # | 差距 | 影响 | 改进方向 | 优先级 |
|---|------|------|---------|--------|

| # | 差距 | 影响 | 改进方向 | 优先级 |

## 5. P1 — 架构/代码质量问题

### 5.1 循环依赖: page_composer_service ↔ service

- **现状**: `page_composer_service.py` 通过延迟导入引用 `wiki.service` 的私有辅助函数 (`_collect_nodes_by_depth` 等)
- **风险**: 类型检查失效、导入顺序敏感
- **修复**: 将共享辅助函数提取到 `wiki/helpers.py`

### 5.2 两套并行的 System Overview 实现

- **现状**:
  - `synthesize_overviews_node` (pipeline_nodes.py): 简化版，仅用前 200 字符
  - `SystemOverviewComposer` (system_overview_composer.py): 完整版 7-section prompt
- **风险**: 内容质量不一致，维护两套代码
- **修复**: pipeline node 复用 `SystemOverviewComposer`

### 5.3 Diagram dict shape 不一致

- **现状**: pipeline 中 `page_dict["diagrams"]` 用 `diagram_type` key；`WikiPage.from_dict` 期望 `type`
- **风险**: round-trip 时图表数据丢失
- **修复**: 统一 key 名称或在 `from_dict` 中兼容两种格式

### 5.4 pipeline 节点命名残留

- `collect_modules` 节点实际执行 `classify_entities_node` (实体角色分类)
- **修复**: 重命名为 `classify_entity_roles`

### 5.5 prompts.py 废弃模板

- `DOMAIN_CLASSIFY_PROMPT` / `TOPIC_STRUCTURE_PROMPT` 仅测试引用
- 生产代码使用各 planner/composer 的内联字符串
- **风险**: 测试与生产行为不一致
- **修复**: 删除废弃模板或将内联 prompt 迁入

## 6. P1 — 前端体验问题

### 6.1 i18n 不一致 (12+ 组件)

| 组件 | 问题 |
|------|------|
| `WikiTopicContent` | 硬编码中文 ("页面内容尚未生成", "已审批", "待修改") |
| `WikiDomainReviewPanel` | 繁体/简体混合 ("0 個模塊") |
| `WikiTopicTreeNav` | 中文 aria-label |
| `WikiKnowledgeGraph` | "加载中...", "加载失败" |
| `WikiShell` | "主题树" / "代码结构" 硬编码 |
| `WikiBusinessFlowGraph` | "Loading flows..." (English) |

**修复**: 统一使用 `useI18n` 的 `t.wiki.*` namespace

### 6.2 Domain Review 模块计数错误

- `mapTopicTreeToDomainPanelNodes` 始终设置 `modules: []`
- 审查面板显示 "0 个模块"
- **修复**: 从 domain tree API 传递实际 module 列表

### 6.3 AskPanel 缺少页面上下文

- 当前 AskPanel 全局级别，未自动将当前查看的 wiki 页面作为 context
- **修复**: 将 `currentPage.content` 作为 conversation context 自动注入

### 6.4 Cache invalidation 过广

- `invalidateWikiQueriesForBusiness` 无视 `businessId`，刷新所有 `wiki` query
- 多 business 场景下导致不必要的重新加载
- **修复**: 规范化 queryKey 格式为 `["wiki", businessId, ...]`

### 6.5 审批按钮缺少 loading 状态

- 域审批后立即关闭面板，不等待 mutation 完成
- 审批/拒绝按钮无 `isPending` disabled 状态
- **修复**: 使用 mutation 的 `isPending` 禁用按钮，`onSuccess` 后关闭面板

### 6.6 SSE 断连无 UI 反馈

- `useWikiEvents` 有重连逻辑但无 "disconnected" / "reconnecting" 提示
- **修复**: 添加连接状态指示器
